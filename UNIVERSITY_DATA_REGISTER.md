# UNIVERSITY_DATA_REGISTER.md

**Single source of truth:** `site/src/content/universities/<slug>.json`, validated at build time by the schema in `site/src/content/schema.mjs` (wired into the collections by `site/src/content.config.ts`; the same schema file is used by `npm run test:records`). This document explains the model, the verification process and the current state of each record. It does not duplicate the data.

## 1. Data model (summary) — extended 2026-10-11

Every factual field is a **claim**: `{ value, status, source, checked, note }`.

| `status` | Meaning | How pages render it |
|---|---|---|
| `verified` | Checked against the official source in `source` on date `checked` | Shown as fact with "Verified", source link and date |
| `unverified` | Reported value (search-snippet lead, brief, earlier list) not yet checked — **must carry a `note` saying where it came from** | Shown highlighted with "Verification pending" and a warning; never as plain fact |
| `outdated` | Was verified, but the source has changed or the academic year has passed | Treated like unverified until re-checked |
| `not-published` | We deliberately hold no value (e.g. a fee we have not read on the official page) | "To be confirmed" — nothing invented |

**Record level:** `slug`, `synthetic` (true only for the sample record in `site/src/content/samples/`), `officialName`, `shortName`, `alternativeNames`, `status` (operating / relocated / merged / suspended / unknown), `statusStatement` (the university's own dated statement for the current year, verbatim), `teachingFormat`, `city`, `region`, `address`, `website`, `internationalOffice`, `founded`, `overview`, `accreditation`, `recognition`, `accommodation`, `programmes[]`, `preparatoryRoutes[]`, `researchReferences[]`, `faqs[]`, `images[]` (credit, licence, source, retrieval date), `verification { publishable, lastReview, reviewer, openQuestions }`.

**Programme level (one object per programme; a university may have several per family):** `id`, `name` (as the university names it), `field` ∈ {medicine, dentistry, pharmacy, nursing, public_health, physical_therapy, physical_education, preparatory, other}, `level` ∈ {bachelor, master, integrated_master, junior_bachelor, preparatory, phd, other} (a claim), `specialtyCode`, `qualification` (exact award title — never "MBBS"/"BSN"/"MSN" unless the university uses it), `durationYears`, `durationText` (as printed), `language`, `format`, `internationalAdmission`, `intakeYear` (the intake the programme-level claims refer to), `tuition { amount, currency, per, academicYear, schedule, variesByYear }`, `otherMandatoryCosts[]`, `requirements[]`, `documents[]`, `deadlines`, `intake`, `gradingNote`; the legacy summary lists `entryRequirements` and `requiredDocuments` are retained.

**Requirement object (intake-specific, verbatim):** `{ id, type ∈ subject | grade | exam | language | age | document | other, summary, subject?, minimum? { value, scale }, condition?, examFormat?, intakeYear?, status, source, checked, note }`. Only `verified` requirement objects feed a readiness assessment (APPLICATION_SYSTEM_SPEC §8). Academic subjects and grading scales live here (`subject`, `minimum.scale`) exactly as the university states them.

**Document object:** `{ id, name, condition?, formatNote?, intakeYear?, status, source, checked, note }` — `condition` makes a document conditional (e.g. legalisation for the remote route).

**Preparatory route object:** `{ id, name, languageOfInstruction, englishTrack, durationText, subjects, certificateName, progressionText (verbatim), appliesToEnglishDegreeTrack, startDate, fee, eligibilityText, note }` — every field a claim; the profile prints the standing sentence that a preparatory course does not guarantee admission, and quotes `progressionText` only once verified.

**Research reference:** `{ label, url, purpose, snippetDate?, note? }` — the official pages a verification pass must open. **A research reference is never evidence**; it renders only on draft pages in a preview build.

**Publication gate (changed 2026-10-11).** `verification.publishable = false` ⇒ the record produces **no page at all** in a production build, is absent from the sitemap, from every list, link, form select and JSON-LD block. It is built only with `PREVIEW_UNPUBLISHED=1` (`npm run build:preview` → `dist-preview/`), where every page carrying it is `noindex`, has no canonical / `og:url` / sitemap link / JSON-LD, and shows a draft banner. `publishable = true` is accepted by `test:records` only when `officialName`, `status`, `website` and `address` are verified, `lastReview` is set, there are no open questions, and every programme's `internationalAdmission` is verified. **Behaviour change versus the live site:** the currently live `noindex` Ternopil profile URL will return 404 after the next deploy from this branch (see HOSTING_AND_DEPLOYMENT_ASSESSMENT.md §13) — this requires the owner's explicit acknowledgement before any deployment.

**Hard rule enforced by `test:records`:** a tuition, fee, other-cost or deadline *value* may exist only with `status = verified`. Leads about fees or dates go in `note` text, never in `value`.

**Deferred programmes (owner decision 2026-10-11, rule R9).** `programmes[]` holds only programmes for which an official page gives at least a lead that international applicants are admitted; every other programme the university runs is recorded in `deferredProgrammes[]` with the same structure. Deferred programmes are never rendered on a public page (the gate test checks published profiles) and appear only in the preview verification queue; a programme moves to `programmes[]` once an official page states eligibility, and must then be verified like any other. Where a fee, deadline or intake cannot be confirmed for the current intake, the profile shows "To be confirmed" with a plain-language explanation (owner decision 3). The verification baseline is the 2026–27 intake, but the exact year and wording printed by each university is what gets recorded (owner decision 4).

University fees are never mixed with our own service fees (which do not exist in the data model at all).

## 2. Inclusion criteria for the directory (PROPOSED)

An institution is listed only when all of the following are evidenced:
1. It currently operates as a higher-education institution in Ukraine (official site live; present in a Ministry of Education / EDEBO register).
2. It offers at least one programme in medicine, dentistry, nursing or pharmacy leading to a recognised qualification.
3. It publishes an admissions route for international students (or explicitly states none — in which case it is listed with `internationalAdmission = false`).
4. Its current official name is confirmed; merged or renamed predecessors are recorded as `alternativeNames`, not as separate entries.
5. Relocated institutions (occupied-territory origins) are listed under their current operating city with `status = relocated`.

Completeness sources (official, identified 2026-10-10 by search; none yet fetched from this environment):
- **MoES "Study in Ukraine" university directory** — `universities.studyinukraine.gov.ua/en/minedu/university/<id>/` (contacts, invitation procedure per institution).
- **EDEBO** — `info.edbo.gov.ua` (Unified State Electronic Database on Education: licences, programmes; Ukrainian only).
- **NAQA accreditation register** — `naqa.gov.ua`.
- **World Directory of Medical Schools** — `search.wdoms.org` (listing only; never "recognised in country X").
Cross-check against the Wikipedia research list in the brief (research inventory only).

## 2a. How the data is edited (Option C rungs)

- **Rung 0 (current):** edit the JSON file on GitHub (web editor or local clone); `npm test` / CI validates the schema and fails on errors.
- **Rung 1 (prepared, inert):** `.pages.yml` at the repository root describes every claim field for Pages CMS, a free git-based editor with a form UI (status dropdown, source URL, check date). It activates only if the owner installs the Pages CMS GitHub App on the repository — an access decision, not a code change. Decap or Sveltia CMS are equivalent alternatives (they need an OAuth relay).
- **Rung 2 (on trigger only):** Kirby Panel — see `PROJECT_EXECUTION_PLAN.md` §2.

## 3. Verification procedure (per university, per intake)

1. Open the official website; record the domain in `website.source`.
2. For each claim, find the official page or PDF; paste its URL into `source`, set `checked` to today, set `status = verified`.
3. Fees: copy amount, currency, per-period and academic year exactly; record the payment schedule; never convert currencies.
4. If a page does not publish a fact, set `status = not-published` and explain in `note`.
5. Record the session in `SOURCE_VERIFICATION_REGISTER.md`.
6. When every programme the page shows has verified `language`, `level`, `durationText`/`durationYears`, `internationalAdmission` and `tuition` (or explicit `not-published`), and the record-level identity fields are verified with no open questions, set `verification.publishable = true` and `lastReview`.
7. Re-run `npm test`: `test:records` validates the schema and the evidence invariants (R1–R8 in `site/tests/records-evidence.mjs`); the build fails on schema errors; `test:gate` fails if an unpublished record leaks into the production build in any form; `test:preview` renders and audits every draft.
8. Diary a re-check before the next intake; set `outdated` when the academic year passes.

## Publication policy (fail-closed)

*Added 2026-10-11 (branch `wip/pubgate`, backlog N23). Code: `site/src/lib/publication.mjs` (the rules), `site/src/lib/evidence.mjs` (the evidence format), `site/src/lib/records.ts` (the only way pages get university data).*

**In one sentence:** a fact about a university appears on the public site only when the record marks it verified **and** the evidence store holds a matching, quoted, dated entry from an allowed official source; anything else is shown as "To be confirmed", and research notes never appear.

**The evidence store.** One file per record, `site/data/evidence/<slug>.json`, outside `src/content` and `public/`, so it is never served. Each entry names the claim it supports (`claimPath`, e.g. `officialName`, `programmes.medicine.tuition`, `programmes.medicine.requirements.bio`), the exact `value`, the official `sourceUrl`, a `sourceTier`, the `quotation` as published, the date it was read (`accessed`), its `status` (verified, partially-verified, conflicting, unverified, outdated, not-applicable), a `nextReview` date and a `decision` (publish or withhold, with the reason). For a requirement or document item the `value` is the item's content: requirement `{ type, summary, subject?, minimum?, condition?, examFormat?, intakeYear? }`, document `{ name, condition?, formatNote?, intakeYear? }`. A missing file means "nothing verified". An invalid file counts as missing. Today no file exists, because no official page can be opened from this environment.

**When a fact is shown.** All of these must hold:
1. The record marks the claim `verified`, with a value, an https `source` and a `checked` date (not in the future). The official website value, and the international office's web address if it has one, must themselves be https addresses. An object value other than a fee, the international office or the application dates has no public form and is withheld.
2. At least one evidence entry for the same `claimPath` is `verified`, has `decision: "publish"`, a quotation, an `accessed` date (not in the future), an https `sourceUrl` equal to the record's `source`, and exactly the same value (deep-equal: no extra or missing keys, no extra spaces).
3. The source tier is allowed: recognition needs tier 4 (the recognition authority of the destination country), and its page must not be on the university's own website (the host of the `website` value, or any host its tier 1 or 2 entries cite); everything else needs tier 1, 2 or 3. Tier 5 supports nothing.
4. The source address fits its tier. Tier 1 and 2 pages must be on the official website recorded in the record's `website` field (or a subdomain of it). Tier 3 pages must be on a Ukrainian government address ending `.gov.ua`. Tier 4 pages are not checked against a list of authorities: the reviewer must confirm that the page belongs to the destination country's recognition authority. At any tier, these are never evidence: search engines and their results (Google, including Google Docs and Drive, Bing, Yahoo, Yandex, Baidu, DuckDuckGo, Ecosia, Startpage, Ask, Brave Search), cached or translated copies (googleusercontent, translate.goog), archive copies (web.archive.org and other archive hosts, archive.ph, archive.is, archive.today), Wikipedia, Wikiwand and Wikimedia, the WDOMS directory, social media and messaging (Facebook, Instagram, YouTube, TikTok, Twitter, X, LinkedIn, Reddit, Quora, Telegram, WhatsApp), blogs (Medium, Blogspot, WordPress) and link shorteners (bit.ly, tinyurl.com). Neither is an entry whose `method` mentions a snippet, a search result or search engine, or a cached copy. An `owner-capture` entry must name its `captureRef`.
5. No entry for that claim is `conflicting`, no verified entry gives a different value, and no entry lists a contradiction for it in `contradicts` (from either side). If sources disagree, the fact is withheld ("Official sources give different information"). To close a contradiction after the university clarifies, mark the superseded entry `outdated`.
6. An entry whose `nextReview` date has passed no longer counts, for any fact. Time-sensitive facts (statement for the current year, teaching format, fees and other costs, deadlines, intake, intake year, requirements, documents, preparatory fee and start date) must also have a `nextReview` date. An entry that names an academic year that has ended (for example 2025/26 during 2026/27) no longer counts. Fees need an academic year that has not ended, and the evidence must name the same year. An intake year that has ended is withheld, and so is a requirement or document whose `intakeYear` has ended. The current-year statement needs evidence naming the current academic year or dated within it. A deadline that has passed is never shown, and a deadline must be written YYYY-MM-DD.
7. The value carries no wording from a research note. The words checked, in any letter case, are: "search snippet" (also "search-snippet"), "snippet lead", "not verified", "not yet verified", "unverified", "awaiting verification", "pending verification", "draft record", "read the official page", "before publishing", "research lead", "research note", "research reference", "to be confirmed", "TBC", "TODO", "FIXME", "placeholder" and "lorem ipsum". A cost whose label carries this wording is left out. The same wording in our own text (short name, city, region, overview, or the name of a listed programme or shown preparatory route) blocks publication of the whole profile.

Anything else: the page prints "To be confirmed" with a fixed explanation. The value, the note and the source are not printed. Unverified requirement, document and cost items are left out. When some are left out, the page says so: "Some requirements are still being confirmed …" (or "Some documents …") below the verified ones, "No requirement has been verified for this programme yet" (or "No document requirement …") when none is verified, and an "Other mandatory costs: To be confirmed" row for costs. A preparatory route is shown only when at least one of its facts is verified; when every route is withheld, the profile says "To be confirmed", never "None recorded". Items, routes or programmes that share an id are all withheld, because their evidence entries cannot be told apart.

**Fields that never appear publicly.** Every field of the record has a class in `FIELD_POLICY`: *public* (shown once its evidence passes), *editorial-public* (our own text, e.g. slug, short name, city, overview, programme name) or *internal*. Internal: notes, research references, deferred programmes, open questions, the reviewer, alternative names, FAQs and images (no publication rule yet), grading notes, the legacy summary lists, the synthetic flag, each claim's own `status` (pages see only the policy's result) and the publishable flag itself. A new field added to `site/src/content/schema.mjs` without a class makes the tests and every build fail, so nobody can add a field to public pages without deciding about it.

**When a profile is published.** The `publishable` flag can only narrow the decision. A record is published only when the flag is `true` **and** all of these pass:
- an evidence file exists and is valid;
- the slug uses only lower-case letters, digits and single hyphens;
- official name, official website, address, operating status, the university's statement for the current year and the teaching format are all shown (status operating or relocated; teaching format not "unknown");
- at least one programme can be listed. A programme is listed only when its id uses only letters, digits, "-" and "_" and no other programme (listed or deferred) has the same id, its international admission (open), level, language, duration and intake year are shown, and its fee page has been read. "Read" means an evidence entry for its tuition, whatever the outcome, that is not `outdated`, is at tier 1 or 2 on the official website, was not read from a search snippet, cache or archive, has an `accessed` date that is not in the future, a `nextReview` date that has not passed and no academic year that has ended. Other programmes are left off the page;
- `verification.lastReview` is set, not in the future and no more than 180 days old;
- our own text carries no research-note wording (rule 7 above);
- there are no open questions;
- it is not a synthetic sample.

If the flag is `true` but a check fails, a production build **stops** with an error that names the record and each failure. A preview build still renders the record as a draft and lists the failures in its verification queue.

**Commands** (from `site/`):

| Command | What it does |
|---|---|
| `node scripts/publication-report.mjs` | For every record: flag, policy result, and each failure in plain words. Add a slug to report one record. |
| `npm run test:records` | Schema and evidence rules R1–R11: R6 runs the policy for every flagged record and also requires `programmes[]` to be trimmed; R10 requires a matching verified evidence entry for every claim marked verified; R11 validates every evidence file. |

**What a reviewer does to publish a profile.**
1. Open each official page in a browser and save a capture showing the address and the date (filed outside the repository).
2. For each fact: in the record, set `status: "verified"`, `source` (the page address) and `checked` (today); in `site/data/evidence/<slug>.json`, add an entry with the same `claimPath`, the identical `value`, the same address as `sourceUrl`, the tier, the exact quotation, `accessed`, `status: "verified"`, `decision: "publish"`, and for time-sensitive facts a `nextReview` date (before the next intake) and, for fees, the `academicYear`.
3. Read the fee page for each programme you want listed, and record what it says: the fee, or an entry with `decision: "withhold"` explaining what the page does not say.
4. Where two official sources disagree, add both entries, mark the second `conflicting` with `contradicts`, and leave the fact withheld until the university clarifies. When it does, mark the superseded entry `outdated`.
5. Answer or close every open question, set `lastReview` to today, then set `publishable: true`.
6. Run `node scripts/publication-report.mjs <slug>` until it says "Every publication check passes", then `npm test`.
7. Check the profile in the preview build against the captures before asking the owner to approve a release.
