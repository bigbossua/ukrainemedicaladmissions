# UNIVERSITY_DATA_REGISTER.md

**Single source of truth:** `site/src/content/universities/<slug>.json`, validated at build time by the schema in `site/src/content/schema.mjs` (wired into the collections by `site/src/content.config.ts`; the same schema file is used by `npm run test:records`). This document explains the model, the verification process and the current state of each record. It does not duplicate the data.

## 1. Data model (summary) — extended 2026-10-11

Every factual field is a **claim**: `{ value, status, source, checked, note }`.

| `status` | Meaning | How pages render it |
|---|---|---|
| `verified` | Checked against the official source in `source` on date `checked` | Shown as fact with "Verified", source link and date |
| `unverified` | Reported value (search-snippet lead, brief, earlier list) not yet checked — **must carry a `note` saying where it came from** | Shown highlighted with "Verification pending" and a warning; never as plain fact |
| `outdated` | Was verified, but the source has changed or the academic year has passed | Treated like unverified until re-checked |
| `not-published` | We deliberately hold no value (e.g. a fee we have not read on the official page) | "To be confirmed" — nothing invented |

**Record level:** `slug`, `synthetic` (true only for the sample record in `site/src/content/samples/`), `officialName`, `shortName`, `alternativeNames`, `status` (operating / relocated / merged / suspended / unknown), `statusStatement` (the university's own dated statement for the current year, verbatim), `teachingFormat`, `city`, `region`, `address`, `website`, `internationalOffice`, `founded`, `overview`, `accreditation`, `recognition`, `accommodation`, `programmes[]`, `preparatoryRoutes[]`, `researchReferences[]`, `faqs[]`, `images[]` (credit, licence, source, retrieval date), `verification { publishable, lastReview, reviewer, openQuestions }`.

**Programme level (one object per programme; a university may have several per family):** `id`, `name` (as the university names it), `field` ∈ {medicine, dentistry, pharmacy, nursing, public_health, physical_therapy, physical_education, preparatory, other}, `level` ∈ {bachelor, master, integrated_master, junior_bachelor, preparatory, phd, other} (a claim), `specialtyCode`, `qualification` (exact award title — never "MBBS"/"BSN"/"MSN" unless the university uses it), `durationYears`, `durationText` (as printed), `language`, `format`, `internationalAdmission`, `intakeYear` (the intake the programme-level claims refer to), `tuition { amount, currency, per, academicYear, schedule, variesByYear }`, `otherMandatoryCosts[]`, `requirements[]`, `documents[]`, `deadlines`, `intake`, `gradingNote`; the legacy summary lists `entryRequirements` and `requiredDocuments` are retained.

**Requirement object (intake-specific, verbatim):** `{ id, type ∈ subject | grade | exam | language | age | document | other, summary, subject?, minimum? { value, scale }, condition?, examFormat?, intakeYear?, status, source, checked, note }`. Only `verified` requirement objects feed a readiness assessment (APPLICATION_SYSTEM_SPEC §8). Academic subjects and grading scales live here (`subject`, `minimum.scale`) exactly as the university states them.

**Document object:** `{ id, name, condition?, formatNote?, intakeYear?, status, source, checked, note }` — `condition` makes a document conditional (e.g. legalisation for the remote route).

**Preparatory route object:** `{ id, name, languageOfInstruction, englishTrack, durationText, subjects, certificateName, progressionText (verbatim), appliesToEnglishDegreeTrack, startDate, fee, eligibilityText, note }` — every field a claim; the profile prints the standing sentence that a preparatory course does not guarantee admission, and quotes `progressionText` only once verified.

**Research reference:** `{ label, url, purpose, snippetDate?, note? }` — the official pages a verification pass must open. **A research reference is never evidence**; it renders only on draft pages in a preview build.

**Publication gate (changed 2026-10-11; research previews added 2026-10-12).** `verification.publishable = false` ⇒ the record gets **no full profile** in a production build and is absent from the sitemap, from every JSON-LD block and from fee, course and comparison content. **Exception (N25, `PUBLICATION_POLICY_DECISIONS.md` (d)):** while `RESEARCH_PREVIEWS` is on, a real record that opts in (`verification.researchPreview: true`, set on all 12) is listed as a research preview: its short name with the label "Not yet verified" on `/universities/` and the home page, a "(not yet verified)" choice in the home and `/apply/` forms, and a `noindex, follow` page at `/universities/<slug>/` built only from the policy projection (`toPublicRecord`), so it shows only claims the evidence store verifies (none today), with no structured data and no sitemap entry. A record that does not opt in leaves no trace. The full record is built only with `PREVIEW_UNPUBLISHED=1` (`npm run build:preview` → `dist-preview/`), where every page carrying it is `noindex`, has no canonical / `og:url` / sitemap link / JSON-LD, and shows a draft banner. `publishable = true` is accepted by `test:records` only when `officialName`, `status`, `website` and `address` are verified, `lastReview` is set, there are no open questions, and every programme's `internationalAdmission` is verified. **Behaviour change versus the live site:** the currently live `noindex` Ternopil profile URL stays at the same address but, after the next deploy from this branch, serves the labelled research preview instead of the old unverified profile (the temporary 302 chosen on 2026-10-11 was removed on 2026-10-12; see HOSTING_AND_DEPLOYMENT_ASSESSMENT.md §13) — this requires the owner's explicit acknowledgement before any deployment.

**Hard rule enforced by `test:records`:** a tuition, fee, other-cost or deadline *value* may exist only with `status = verified`. Leads about fees or dates go in `note` text, never in `value`.

**Deferred programmes (owner decision 2026-10-11, rule R9).** `programmes[]` holds only programmes for which an official page gives at least a lead that international applicants are admitted; every other programme the university runs is recorded in `deferredProgrammes[]` with the same structure. Deferred programmes are never rendered on a public page (the gate test checks published profiles) and appear only in the preview verification queue; a programme moves to `programmes[]` once an official page states eligibility, and must then be verified like any other. Where a fee, deadline or intake cannot be confirmed for the current intake, the profile shows "To be confirmed" with a plain-language explanation (owner decision 3). The verification baseline is the 2026–27 intake, but the exact year and wording printed by each university is what gets recorded (owner decision 4).

University fees are never mixed with our own service fees (which do not exist in the data model at all).

## 2. Inclusion criteria for the directory (PROPOSED)

An institution is listed only when all of the following are evidenced:
1. It currently operates as a higher-education institution in Ukraine (official site live; present in a Ministry of Education / EDEBO register).
2. It offers at least one programme in medicine, dentistry, nursing or pharmacy leading to a recognised qualification.
3. It publishes an admissions route for international students (or explicitly states none — in which case it is listed with `internationalAdmission = false`).
4. Its current official name is confirmed; merged or renamed predecessors are recorded as `alternativeNames`, not as separate entries.
5. Relocated institutions (occupied-territory origins) are listed under their current operating city with `status = relocated`.

Completeness sources (official, identified 2026-10-10 by search; none yet fetched from this environment):
- **MoES "Study in Ukraine" university directory** — `universities.studyinukraine.gov.ua/en/minedu/university/<id>/` (contacts, invitation procedure per institution).
- **EDEBO** — `info.edbo.gov.ua` (Unified State Electronic Database on Education: licences, programmes; Ukrainian only).
- **NAQA accreditation register** — `naqa.gov.ua`.
- **World Directory of Medical Schools** — `search.wdoms.org` (listing only; never "recognised in country X").
Cross-check against the Wikipedia research list in the brief (research inventory only).

## 2a. How the data is edited (Option C rungs)

- **Rung 0 (current):** edit the JSON file on GitHub (web editor or local clone); `npm test` / CI validates the schema and fails on errors.
- **Rung 1 (prepared, inert):** `.pages.yml` at the repository root describes every claim field for Pages CMS, a free git-based editor with a form UI (status dropdown, source URL, check date). It activates only if the owner installs the Pages CMS GitHub App on the repository — an access decision, not a code change. Decap or Sveltia CMS are equivalent alternatives (they need an OAuth relay).
- **Rung 2 (on trigger only):** Kirby Panel — see `PROJECT_EXECUTION_PLAN.md` §2.

## 3. Verification procedure (per university, per intake)

1. Open the official website; record the domain in `website.source`.
2. For each claim, find the official page or PDF; paste its URL into `source`, set `checked` to today, set `status = verified`.
3. Fees: copy amount, currency, per-period and academic year exactly; record the payment schedule; never convert currencies.
4. If a page does not publish a fact, set `status = not-published` and explain in `note`.
5. Record the session in `SOURCE_VERIFICATION_REGISTER.md`.
6. When every programme the page shows has verified `language`, `level`, `durationText`/`durationYears`, `internationalAdmission` and `tuition` (or explicit `not-published`), and the record-level identity fields are verified with no open questions, set `verification.publishable = true` and `lastReview`.
7. Re-run `npm test`: `test:records` validates the schema and the evidence invariants (R1–R8 in `site/tests/records-evidence.mjs`); the build fails on schema errors; `test:gate` fails if an unpublished record leaks into the production build in any form other than its research preview (slug, short name and verified claims only); `test:preview` renders and audits every draft.
8. Diary a re-check before the next intake; set `outdated` when the academic year passes.

## 7. Comparison framework for prospective students (how universities will be compared — no rankings)

Only fields with `status = verified` are compared; anything else is shown as "not published" or "awaiting verification". The directory's comparison table and each profile use the same fields in the same order:

| Field | Shown as | Rule |
|---|---|---|
| Programmes open to international applicants | list with award title and duration | from verified programme records |
| Language of instruction per programme | English / Ukrainian / both | verified per programme, not per university |
| Entry requirements per programme | subjects, grades/scale, exams, language level | verified requirement objects only; "not published" otherwise |
| Preparatory route | yes/no, duration, language, progression condition text | verified; progression text copied from the official page |
| Tuition (per year, currency, academic year) | exact figures with year and source | never converted, never averaged, never "from $" |
| Application window / deadlines | dates with the intake year | verified for the current cycle only |
| Location and current status | city; operating / relocated / blended; last official notice date | from official notices; undated snippets are not status evidence |
| Recognition | regulator statements only, from the destination-country regulator's own source, with date (a World Directory of Medical Schools listing is a directory entry, not evidence of recognition, and is not shown: `source-not-evidence`) | never "recognised in country X" as our claim |
| Last verified | date | shown on every card and profile |

Words the site never uses about a university: best, top, safest, cheapest, most recognised, guaranteed, partner (unless a written agreement exists and is cited).

## 10. How the directory and candidate-profile system support many universities and programmes — IMPLEMENTED locally 2026-10-11

- **One source of truth:** `site/src/content/universities/<slug>.json` holds record-level and programme-level claims; programmes carry `field`, `level`, `specialtyCode`, `qualification`, `language`, `durationText`, `internationalAdmission`, `intakeYear`, `tuition`, structured `requirements[]` and `documents[]`; the record carries `preparatoryRoutes[]` and `researchReferences[]`. Schema: `site/src/content/schema.mjs`.
- **No separate SEO page per programme.** Programme families beyond the four course pages (public health, physical therapy/rehabilitation, physical education/sport, preparatory, other) are supported in the directory filters, on the profile and in the candidate-profile service without any new URL (`site/src/lib/fields.ts`: `page: null`). KEYWORD_URL_MAP.md §7 remains the only route to a new indexable page.
- **Directory** (`/universities/`): filters by city, programme family, qualification level, teaching language, preparatory route and intake, driven by data attributes on each card; count and empty state; a side-by-side comparison table built **only from verified claims** (unverified cells read "awaiting verification"/"not published"; alphabetical order, no ranking). With zero publishable records the production directory shows an explicit empty state, followed (since 2026-10-12, N25) by the research previews: one card per opted-in record with its short name and "Not yet verified", a name search that accepts spelling variants (e.g. Odessa→Odesa) and, since milestone 2 (2026-10-12), never presents a separate institution with a similar name as a match: a card is a full match only when every word typed is in its name and the query is not a look-alike name from the inventory; otherwise the nearest names appear under a caution that names no institution (`site/src/lib/name-search.mjs`, `npm run test:search`), and fact filters that use verified data only.
- **Profile** (`/universities/<slug>/`): header with status/teaching chips, an at-a-glance block (families, levels, languages, preparatory route), facts list, one card per programme (qualification, code, duration, language, format, intake, fee, application window, intake-specific requirements, documents, CTA `Apply Online Now`), preparatory-route cards with the standing "does not guarantee admission" sentence, sources and verification. Structured data only for a publishable record and only from verified fields.
- **Preview** (`npm run build:preview` → `dist-preview/`, never deployed): draft records render with a draft banner, noindex and no canonical/JSON-LD/sitemap, plus the internal verification queue (research references + open questions); `/preview/` lists drafts and samples and demonstrates the directory and comparison layouts; `/preview/<sample>/` renders the synthetic record.
- **Candidate profile** (APPLICATION_SYSTEM_SPEC §8) will compare a candidate's record with the verified requirement objects of each selected programme and list gaps per programme, with the university's preparatory route shown where verified. Not built in this phase (Stage 2, gated).
- **Nothing hard-coded:** the profile template, the filters, the comparison table, the home/apply selects and the tests iterate over whatever records pass the publication gate; Ternopil is one record among seven.
- **Operating-status guard (policy, to be enforced when the first record is verified):** a record whose `status` is not `operating` or `relocated` with a dated official statement within the current academic year must not be made publishable.

## Publication policy (fail-closed)

*Added 2026-10-11 (branch `wip/pubgate`, backlog N23); extended 2026-10-12 (branch `wip/policy`, backlog N24). Code: `site/src/lib/publication.mjs` (the rules), `site/src/lib/publication-config.mjs` (the settings the owner may change), `site/src/lib/evidence.mjs` (the evidence format), `site/src/lib/records.ts` (the only way pages get university data).*

**Owner settings (N24, 2026-10-12).** Three decisions are still open and run on fail-closed defaults until the owner confirms or changes them: our own text (overview, programme names, city, region), which hosts count as a recognition authority, and whether the official website needs a government listing. A fourth, research previews (N25, decision (d)), is on by default and described below. Each is a named constant in `site/src/lib/publication-config.mjs`; `PUBLICATION_POLICY_DECISIONS.md` (repository root) gives the exact backlog wording, the options, what each means for students and for the business, and how to change it. The rules below describe the defaults.

**In one sentence:** a fact about a university appears on the public site only when the record marks it verified **and** the evidence store holds a matching, quoted, dated entry from an allowed official source; anything else is shown as "To be confirmed", and research notes never appear.

**The evidence store.** One file per record, `site/data/evidence/<slug>.json`, outside `src/content` and `public/`, so it is never served. Each entry names the claim it supports (`claimPath`, e.g. `officialName`, `programmes.medicine.tuition`, `programmes.medicine.requirements.bio`), the exact `value`, the official `sourceUrl`, a `sourceTier`, the `quotation` as published, the date it was read (`accessed`), its `status` (verified, partially-verified, conflicting, unverified, outdated, not-applicable), a `nextReview` date and a `decision` (publish or withhold, with the reason). For a requirement or document item the `value` is the item's content: requirement `{ type, summary, subject?, minimum?, condition?, examFormat?, intakeYear? }`, document `{ name, condition?, formatNote?, intakeYear? }`. A missing file means "nothing verified". An invalid file counts as missing. Today no file exists, because no official page can be opened from this environment.

**When a fact is shown.** All of these must hold:
1. The record marks the claim `verified`, with a value, an https `source` and a `checked` date (not in the future). The official website value, and the international office's web address if it has one, must themselves be https addresses. An object value other than a fee, the international office or the application dates has no public form and is withheld.
2. At least one evidence entry for the same `claimPath` is `verified`, has `decision: "publish"`, a quotation, an `accessed` date (not in the future), an https `sourceUrl` equal to the record's `source`, and exactly the same value (deep-equal: no extra or missing keys, no extra spaces).
3. The source tier is allowed: recognition needs tier 4 (the recognition authority of the destination country), and its page must not be on the university's own website (the host of the `website` value, or any host its tier 1 or 2 entries cite) **and must be on a host the owner has listed in `RECOGNITION_AUTHORITY_HOSTS`** (or a subdomain of one). That list is empty by default, so no recognition claim is shown until the owner chooses the authorities. Fees and other mandatory costs need tier 1 or 2; everything else needs tier 1, 2 or 3. Tier 5 supports nothing.
4. The source address fits its tier. Tier 1 and 2 pages must be on the official website recorded in the record's `website` field (or a subdomain of it), **and only once that website is itself shown**. The website is shown only when, besides every other rule, a verified tier-3 entry on a `.gov.ua` address (for example a Ministry or EDEBO page) carries exactly the same website value, character for character (setting `WEBSITE_REQUIRES_GOVERNMENT_EVIDENCE`). Until then the university's own pages support nothing, so no fact read there is shown and no programme is listed. A verified government entry carrying a different website is a conflict, and everything that depends on the official host stays withheld. Tier 3 pages must be on a Ukrainian government address ending `.gov.ua`. Tier 4 pages must be on a listed recognition authority host (rule 3). At any tier, these are never evidence: search engines and their results (Google, including Google Docs and Drive, Bing, Yahoo, Yandex, Baidu, DuckDuckGo, Ecosia, Startpage, Ask, Brave Search), cached or translated copies (googleusercontent, translate.goog), archive copies (web.archive.org and other archive hosts, archive.ph, archive.is, archive.today), Wikipedia, Wikiwand and Wikimedia, the WDOMS directory, social media and messaging (Facebook, Instagram, YouTube, TikTok, Twitter, X, LinkedIn, Reddit, Quora, Telegram, WhatsApp), blogs (Medium, Blogspot, WordPress) and link shorteners (bit.ly, tinyurl.com). Neither is an entry whose `method` mentions a snippet, a search result or search engine, or a cached copy. An `owner-capture` entry must name its `captureRef`.
5. No entry for that claim is `conflicting`, no verified entry gives a different value, and no entry lists a contradiction for it in `contradicts` (from either side). If sources disagree, the fact is withheld ("Official sources give different information"). To close a contradiction after the university clarifies, mark the superseded entry `outdated`.
6. An entry whose `nextReview` date has passed no longer counts, for any fact. Time-sensitive facts (statement for the current year, teaching format, fees and other costs, deadlines, intake, intake year, requirements, documents, preparatory fee and start date) must also have a `nextReview` date. An entry that names an academic year that has ended (for example 2025/26 during 2026/27) no longer counts. Fees need an academic year that has not ended, and the evidence must name the same year. An intake year that has ended is withheld, and so is a requirement or document whose `intakeYear` has ended. The current-year statement needs evidence naming the current academic year or dated within it. A deadline that has passed is never shown, and a deadline must be written YYYY-MM-DD. A preparatory start date or a free-text intake that contains a date written YYYY-MM-DD that has passed, on its own or inside the text ("2026-09-01 (orientation week)"), is never shown (nor one containing an impossible date such as 2026-02-30), and neither is one that names a year before the current academic year's start year (during 2026/27: "September 2025", "2025/26 intake"). A date written any other way within the current academic year (or with no year) is guarded only by its `nextReview` date, so write start dates as YYYY-MM-DD.
7. The value carries no wording from a research note. The words checked, in any letter case, are: "search snippet" (also "search-snippet"), "snippet lead", "not verified", "not yet verified", "unverified", "awaiting verification", "pending verification", "draft record", "read the official page", "before publishing", "research lead", "research note", "research reference", "to be confirmed", "TBC", "TODO", "FIXME", "placeholder" and "lorem ipsum". A cost whose label carries this wording is left out. The same wording in our own text, as written in the record (short name, city, region, overview, the name of any programme in `programmes[]` or of a shown preparatory route), blocks publication of the whole profile.

**Our own text (N24 a).** The overview, programme names, city and region are our text, not claims, so they have no evidence entry of their own. A published profile prints them only as follows (settings `OVERVIEW_REQUIRES_EDITORIAL_REVIEW`, `PROGRAMME_NAME_REQUIRES_QUOTATION`, `CITY_AND_REGION_REQUIRE_VERIFIED_ADDRESS`):
- *Overview:* only when `verification.editorialReview` records a reviewer, a review date that is not in the future and the SHA-256 of the overview exactly as it is now (`overviewSha256`; get it with `node scripts/publication-report.mjs --overview-hash <slug>`). Any later edit, even one character, hides the overview again until it is re-reviewed. Otherwise the overview is left out.
- *Programme name:* only when the name, as recorded, appears (as whole words, ignoring letter case and repeated spaces; a word joined by a hyphen or apostrophe is one word, so "Medicine" is not found in "Pre-Medicine") in the quotation of an evidence entry that verifies that programme's international admission. A programme whose name cannot be printed is not listed. Record the name exactly as the university prints it.
- *City and region:* each only when it appears, as whole words, in the address the profile shows as verified ("Ivano" is not found in "Ivano-Frankivsk"; the match cannot tell a city from a street of the same name, so check that the city recorded is the one the address names). A withheld city reads "To be confirmed" in the directory's city filter and on the home and course pages, and "City to be confirmed" on cards, the profile and the comparison table; a withheld region is left out. A location is never guessed.

**Fees on the page (N24 e).** A shown fee prints its amount, currency, basis (per year, per semester, for the whole programme, or one-off) and academic year, followed by the year-by-year amounts and the payment schedule exactly as recorded when the verified value carries them. The "To be confirmed" explanation promises only what the display prints.

Anything else: the page prints "To be confirmed" with a fixed explanation. The value, the note and the source are not printed. Unverified requirement, document and cost items are left out. When some are left out, the page says so: "Some requirements are still being confirmed …" (or "Some documents …") below the verified ones, "No requirement has been verified for this programme yet" (or "No document requirement …") when none is verified, and an "Other mandatory costs: To be confirmed" row for costs. A preparatory route is shown only when at least one of its facts is verified; when every route is withheld, the profile says "To be confirmed", never "None recorded". Items, routes or programmes that share an id are all withheld, because their evidence entries cannot be told apart.

**Fields that never appear publicly.** Every field of the record has a class in `FIELD_POLICY`: *public* (shown once its evidence passes), *editorial-public* (our own text, e.g. slug, short name, city, overview, programme name) or *internal*. Internal: notes, research references, deferred programmes, open questions, the reviewer, the editorial review of the overview, alternative names, FAQs and images (no publication rule yet), grading notes, the legacy summary lists, the synthetic flag, each claim's own `status` (pages see only the policy's result) and the publishable flag itself. A new field added to `site/src/content/schema.mjs` without a class makes the tests and every build fail, so nobody can add a field to public pages without deciding about it.

**When a profile is published.** The `publishable` flag can only narrow the decision. A record is published only when the flag is `true` **and** all of these pass:
- an evidence file exists and is valid;
- the slug uses only lower-case letters, digits and single hyphens;
- official name, official website, address, operating status, the university's statement for the current year and the teaching format are all shown (status operating or relocated; teaching format not "unknown");
- at least one programme can be listed. A programme is listed only when its id uses only letters, digits, "-" and "_" and no other programme (listed or deferred) has the same id, its international admission (open), level, language, duration and intake year are shown, its name appears in the quotation that verifies its international admission (see "Our own text"), and its fee page has been read. "Read" means an evidence entry for its tuition, whatever the outcome, that is not `outdated`, is at tier 1 or 2 on the official website, was not read from a search snippet, cache or archive, has an `accessed` date that is not in the future, a `nextReview` date that has not passed and no academic year that has ended. Other programmes are left off the page;
- `verification.lastReview` is set, not in the future and no more than 180 days old;
- our own text carries no research-note wording (rule 7 above);
- there are no open questions;
- it is not a synthetic sample.

If the flag is `true` but a check fails, a production build **stops** with an error that names the record and each failure. A preview build still renders the record as a draft and lists the failures in its verification queue.

**Research previews (N25, 2026-10-12; `PUBLICATION_POLICY_DECISIONS.md` (d)).** An unpublished record may still be *listed* by name. A production build lists it as a research preview only when all of these hold: `RESEARCH_PREVIEWS` is `true` (the default); the record is real (not a synthetic sample); `verification.researchPreview` is `true` (set on all 12 records today); it is not published; its slug is safe; and its short name is plain text of 3 to 120 characters with no markup or research-note wording. A preview then gets:
- a card on `/universities/` and an entry on the home page, each with the short name and the label "Not yet verified", and a choice "(not yet verified)" in the home and `/apply/` forms (choosing it records interest only);
- a page at `/universities/<slug>/` built **only** from the policy projection (`toPublicRecord`), so it shows exactly what a published profile could print: today the name and nothing else, since no claim is verified. The page is `noindex, follow`, has no structured data, is never in the sitemap, says it is not the university's website and claims no partnership, and links to `/apply/?university=<slug>`.

Fee, course and comparison content never lists a preview. A record flagged `publishable: true` that fails the policy still stops the build, whether or not it opts in. With `RESEARCH_PREVIEWS = false`, or for a record that does not opt in, the old rule applies: no card, no page, no mention. Today the gate reports 0 published and 12 research previews. `test:gate` checks every preview page and scans all production files for anything from the record beyond its slug, short name and shown claims.

**What a reviewer does to publish a profile.**
1. Open each official page in a browser and save a capture showing the address and the date (filed outside the repository).
2. Start with the website: read a Ukrainian government page (Ministry portal, EDEBO or another `.gov.ua` register) that lists the university's website, and record it as a tier-3 `website` entry whose `value` is exactly the website as the register prints it (use the same value in the record). Until this entry exists, nothing read on the university's own pages counts.
3. For each fact: in the record, set `status: "verified"`, `source` (the page address) and `checked` (today); in `site/data/evidence/<slug>.json`, add an entry with the same `claimPath`, the identical `value`, the same address as `sourceUrl`, the tier, the exact quotation, `accessed`, `status: "verified"`, `decision: "publish"`, and for time-sensitive facts a `nextReview` date (before the next intake) and, for fees, the `academicYear`. For each programme's international admission, quote the passage that names the programme, and record the programme's name exactly as quoted.
4. Read the fee page for each programme you want listed, and record what it says: the fee, or an entry with `decision: "withhold"` explaining what the page does not say.
5. Where two official sources disagree, add both entries, mark the second `conflicting` with `contradicts`, and leave the fact withheld until the university clarifies. When it does, mark the superseded entry `outdated`.
6. Rewrite the overview so it says nothing beyond the verified facts, read it, and record `verification.editorialReview` (reviewer, today's date, the hash from `--overview-hash`). Write the city and region as they appear in the verified address.
7. Answer or close every open question, set `lastReview` to today, then set `publishable: true`.
8. Run `node scripts/publication-report.mjs <slug>` until it says "Every publication check passes", then `npm test`.
9. Check the profile in the preview build against the captures before asking the owner to approve a release.
