# UNIVERSITY_EVIDENCE_STANDARD.md — how a university claim becomes publishable

**Date:** 2026-10-11 · **Branch:** `wip/evidence` (from `4b93a11`) · **Applies to:** every factual statement about a university, a programme or an admissions route that a page of ukrainemedicaladmissions.com could show.

**Position today (checked in this environment on 2026-10-11).** No university claim is verified. Every official host tried from the build environment was refused at the environment's proxy under its network policy (curl: "CONNECT tunnel failed, response 403"; HTTP code 000), and so were the Ministry portals, the NAQA site, the web archive and the World Directory of Medical Schools (§11.4 and `SOURCE_VERIFICATION_REGISTER.md`). The seven evidence files in `site/data/evidence/` therefore hold **no entries**, only an access block saying so. No university-specific fact may appear in a production page until this standard has been met for it.

**Access limitations are not evidence (POLICY).** A refused connection, timeout or gateway denial from the build environment is a fact about the environment, not about the university. It is recorded only in the evidence file's `access` block; it never creates an evidence entry, never changes a claim's status or value, and never supports "not published" or "not-applicable". The complete list of refused hosts is in `DIRECTORY_VERIFICATION_PLAN.md` §10.1a.

**How to read this document.** Every rule carries one of two labels:

- **POLICY** — binding now. It comes from the owner's rules, the owner's decisions of 2026-10-11 (`DIRECTORY_VERIFICATION_PLAN.md` §8) or the existing record tests (`site/tests/records-evidence.mjs`).
- **TO CONFIRM (owner)** — a working rule the reviewer follows until the owner confirms or changes it. All of them are listed together in §13.

Nothing in this document is a fact about any university. Examples are generic and name no institution.

## 1. Principles (POLICY)

1. A claim is shown as fact only when an acceptable official source states it and the evidence is recorded as this standard describes. Everything else shows as "To be confirmed" (with a plain explanation) or not at all.
2. Never invent or silently assume fees, programme availability, teaching language, requirements, deadlines, degree titles, durations, accreditation, recognition, government approvals, visa or invitation procedures, contact details, international eligibility, application procedures, outcomes, partnerships or agency authority.
3. A search snippet, an agent's page, a directory listing, a blog, social media, an AI summary or an encyclopaedia article is a **lead**. It tells the reviewer where to look. It never counts as evidence, however many leads agree.
4. Every piece of evidence is classified with one of six statuses: verified, partially verified, conflicting, unverified, outdated or not applicable (§5).
5. Professional registration or a licence to practise in a student's home country, or in any other country, is never stated or implied (§9).
6. No claim is copied from one university's record or evidence to another's.

## 2. Where evidence lives (POLICY)

| What | Where | Served on the website? |
|---|---|---|
| The claim as the site would show it | `site/src/content/universities/<slug>.json` — each claim is `{ value, status, source, checked, note }` | Only when the claim is verified and the record is publishable or a research preview (N25: the preview page prints only verified claims) |
| The evidence behind each claim | `site/data/evidence/<slug>.json` — one file per record | **Never.** It sits outside `site/src/content` and `site/public`, so it is never rendered, served or copied into a build output (at most, build-time policy code reads it) |
| The reviewer's work-list | `research/verification/<slug>/EVIDENCE_REGISTER.md`, generated by `site/scripts/make-evidence-register.py` (it shows each claim's evidence entries and the access block) | No |
| Captures of official pages (PDFs, screenshots) | **Outside the repository** (the repository is public). Only the file name is recorded, in `captureRef` | No |
| The audit trail of access attempts | `SOURCE_VERIFICATION_REGISTER.md` | No |

Draft records and evidence never reach the sitemap, navigation, structured data or indexable HTML. Preview-only pages exist only in the preview build (`npm run build:preview`). Since 2026-10-12 an unpublished record that opts in is listed by name as a research preview labelled "Not yet verified", with a `noindex` page built only from the claims the evidence store verifies; its notes, unverified values and evidence never appear (`PUBLICATION_POLICY_DECISIONS.md` (d)).

## 3. The evidence file interface (POLICY — identical for every work package; do not change it)

Copied exactly from the Phase 3 brief:

```
One file per university record: site/data/evidence/<record slug>.json (NOT under site/src/content and NOT under site/public, so it is never served or rendered):
{
  "slug": "<record slug>",
  "access": { "status": "blocked" | "open", "checked": "YYYY-MM-DD", "note": "plain text: which official hosts were tried and what happened" },
  "entries": [
    {
      "id": "<slug>/<claimPath>/<n>",
      "claimPath": "<path>",
      "statement": "the exact claim being evaluated, in words",
      "value": <the JSON value exactly as it would appear in the record claim's value>,
      "sourceUrl": "https://...",
      "sourceOrganisation": "e.g. Vinnytsia National Pirogov Memorial Medical University",
      "sourceTier": 1 | 2 | 3 | 4 | 5,
      "evidenceType": "web-page" | "pdf" | "owner-capture" | "official-letter",
      "quotation": "exact relevant passage as published",
      "effectiveDate": "YYYY-MM-DD" | null,
      "academicYear": "2026/27" | null,
      "accessed": "YYYY-MM-DD",
      "captureRef": "capture file name kept OUTSIDE the repository" | null,
      "status": "verified" | "partially-verified" | "conflicting" | "unverified" | "outdated" | "not-applicable",
      "reviewer": "name or role",
      "method": "how it was checked, e.g. read on the official page in a browser session",
      "contradicts": ["<entry id>", ...],
      "nextReview": "YYYY-MM-DD" | null,
      "decision": "publish" | "withhold",
      "withholdReason": "plain text" | null
    }
  ]
}
claimPath grammar: record-level keys by name (officialName, status, statusStatement, teachingFormat, address, website, internationalOffice, founded, accreditation, recognition, accommodation); programme fields as programmes.<programmeId>.<field> (e.g. programmes.medicine.tuition, programmes.medicine.language); requirement and document items as programmes.<programmeId>.requirements.<requirementId> and programmes.<programmeId>.documents.<documentId>; other costs as programmes.<programmeId>.otherMandatoryCosts.<index>; preparatory routes as preparatoryRoutes.<routeId>.<field>.
Source tiers (prefer the lowest number): 1 official university programme, admissions or tuition page; 2 official university fee schedule or dated admissions announcement (PDF or page); 3 Ukrainian government or competent regulator; 4 official recognition authority of the destination country (the only acceptable tier for a recognition claim); 5 other authoritative primary source. Third-party directories, agents, blogs, social media and search snippets are leads and never evidence.
Today no entry is verified: every official host is blocked from this environment. Files for draft records therefore carry "entries": [] and an access block saying so.
```

The `sourceOrganisation` example in the interface is a placeholder for the field's format only; it is not a verified official name.

## 4. What "verified" requires (POLICY)

A record claim may carry `status: verified` — and so be shown as fact — only when **all** of the following hold:

1. At least one evidence entry exists for its claim path with status `verified` and decision `publish`.
2. That entry has a non-empty `quotation` taken from the source itself. A quotation from a search snippet, an agent, a directory or a summary does not count.
3. Its `sourceTier` is one the claim type accepts (§7).
4. Its `value` is identical to the record claim's `value`, its `sourceUrl` is the record claim's `source`, and its `accessed` date is the record claim's `checked` date.
5. No other entry for the same claim path is `conflicting` or lists it in `contradicts`, unless the conflict has been resolved and recorded (§8).
6. For a time-sensitive claim (§10): `academicYear` is set, it matches the intake the claim is shown for, and `nextReview` has not passed.

Leads never count. A claim supported only by snippets, agent pages, directories, blogs, social media or memory stays unverified, however consistent the leads are.

**Enforcement.** Today `site/tests/records-evidence.mjs` enforces the record side only (R2: a verified claim carries an https source and a check date; R4: money and deadline values exist only when verified). The cross-check between record claims and evidence entries (points 1–6) belongs to the publication-policy code, which another work package owns; until that code exists, the reviewer checks it by hand, helped by the evidence column of the register.

## 5. The six statuses (POLICY)

| Status | Meaning | Decision | Record claim (mapping — TO CONFIRM with the policy code) |
|---|---|---|---|
| `verified` | A source of an acceptable tier states the claim exactly as worded, for the stated academic year where time matters; the exact quotation is recorded; no unresolved conflict; `nextReview` not passed | `publish` (or `withhold` with a reason, e.g. the owner chooses not to show it) | `verified`, with `source` and `checked` from the entry |
| `partially-verified` | The source supports part of the statement but not all of it — for example an amount and currency without the academic year or payment basis, or a programme listed without its teaching language | `withhold` the claim as worded. The supported part may be recorded as its own, narrower claim with its own entry | `unverified` (value kept as a lead, with a note) or `not-published` |
| `conflicting` | Two acceptable sources disagree, or one source contradicts itself | `withhold`; record both (§8) | `unverified` or `not-published`; the note names the disagreeing sources |
| `unverified` | No acceptable source has been read yet, or the source read is silent; any value is a lead | `withhold` | `unverified` (value with a provenance note) or `not-published` |
| `outdated` | Read on an acceptable source, but the source refers to a past academic year or intake, has been replaced by a newer source, or `nextReview` has passed | `withhold` until re-checked | `outdated` |
| `not-applicable` | The claim cannot apply — for example a field of a programme the official page shows is not offered. The reason is recorded | `withhold` (nothing to publish) | `not-published`, with a note |

### 5.1 Recording a silent page (POLICY)

When the reviewer reads the right page and it does not state the fact, that is a valid result: add an entry with status `unverified`, `quotation` `""`, `value` `null`, decision `withhold` and a `withholdReason` such as "page read on 2026-MM-DD; it does not state the application deadline". The record claim becomes `not-published` with a note naming the page read, and the profile shows "To be confirmed" with its explanation (owner decision of 2026-10-11).

## 6. Source hierarchy (POLICY unless marked)

| Tier | Source | Examples of where to look (names only; none opened from this environment) |
|---|---|---|
| 1 | Official university programme, admissions or tuition page | The university's own international-students, admissions or fee pages |
| 2 | Official university fee schedule or dated admissions announcement (PDF or page) | Dated fee PDFs, admission rules for foreign citizens, dated notices on the university's own domain |
| 3 | Ukrainian government or competent regulator | Ministry of Education and Science portals (including the "Study in Ukraine" directory), EDEBO, NAQA |
| 4 | Official recognition authority of the destination country — **the only acceptable tier for a recognition claim** | The authority each destination country names for recognising foreign medical qualifications |
| 5 | Other authoritative primary source | Used only where no lower tier exists and the claim type allows it (§7) |

Prefer the lowest tier number available.

**Ministry portal, EDEBO and NAQA pages** (tier 3 POLICY, from the brief; replacing the older wording TO CONFIRM). They are tier 3 here, because the brief's tier 3 is "Ukrainian government or competent regulator". They are acceptable only for the claim types §7 allows at tier 3, and never for fees or recognition. `DIRECTORY_VERIFICATION_PLAN.md` §6.3, §6.5 and §6.6 were generated before this standard. They still call these pages "cross-check only (not official sources)". This standard replaces that wording; the owner is asked to confirm it (§13 item 17).

**Never evidence:** third-party directories, admissions agents, blogs, social media, forums, search snippets, AI summaries, encyclopaedias, and fee figures on any site other than the university's own.

**Web archive copies** (TO CONFIRM). An archived copy of an official page may document what that page said on the archive date — for example to mark an entry `outdated` or to record a conflict — but it never verifies a current claim.

**World Directory of Medical Schools** (TO CONFIRM). At most tier 5, and only for a bare statement that a school is listed there. A listing is not recognition (§9). Whether such a statement is shown at all is the owner's decision.

**Is the domain the university's own?** (TO CONFIRM). Before relying on a university page, the reviewer confirms that the domain belongs to the university — from a tier 3 listing (Ministry portal or EDEBO) where it can be opened. Until such a check is possible, the `method` says "domain not cross-checked with a register". Some records already carry an open question about which domain is primary.

### 7.1 Fees (POLICY unless marked)

1. Tier 1 or 2 only — the university's own fee page or fee schedule.
2. Record, as printed: the amount; the currency (ISO code in the record); the payment basis — per year, per semester, one-off, or whole programme (the record's `per` field: `year`, `semester`, `once`, `programme`); the academic year; the payment schedule; any year-by-year variation; and whether the charge is refundable — or "not stated" when the page says nothing.
3. Each other mandatory charge gets its own entry under `programmes.<id>.otherMandatoryCosts.<index>`, with its own label, amount, currency, basis and academic year.
4. Never add tuition and other charges into one total. If the university prints a total itself, it may be quoted as the university's total, never recalculated.
5. Never convert currencies, round, estimate, carry a figure from one academic year into another, or use a figure from an agent or another third party. If the page states an exchange-rate basis for payment, record that basis as printed; never compute a converted amount.
6. A page showing a past academic year makes the entry `outdated`; a page with no academic year makes it `partially-verified`. In both cases the fee is withheld and the profile shows "To be confirmed" with its explanation (owner decision of 2026-10-11).
7. **Schema gap (TO CONFIRM).** The record's money object has no field for refundability. Until the owner or the policy-code work package decides, refundability is kept in the evidence entry (statement and quotation) and, where printed, in the money object's `schedule` text; no page may state or imply a refund the source does not state.

## 8. Conflicts (POLICY unless marked)

1. Record every source separately — its own entry, URL, quotation and dates.
2. Set each disagreeing entry to `conflicting` and list the other entry's id in `contradicts`, both ways.
3. Withhold the definitive claim. The record claim is not verified; its note names the official sources that disagree (URLs and dates).
4. The profile shows "To be confirmed" with its explanation; it never picks one figure.
5. **Resolution** (TO CONFIRM). A later dated source for the same academic year supersedes an earlier one only when it says so or is plainly a replacement (for example a revised fee order); the earlier entry then becomes `outdated` with a note. A lower tier number does not by itself settle a disagreement between two official sources. Otherwise the claim stays withheld until the university points to the authoritative page, and that page is read.

## 9. No implication of professional registration (POLICY)

1. No page states or implies that a qualification leads to registration, a licence, eligibility for a licensing examination, or the right to practise in the student's home country or in any other country.
2. A recognition statement appears only from a tier 4 source, quoted, naming the country, the authority and the date. It is accompanied by a plain statement that the student must check with the regulator in their own country before applying (exact wording TO CONFIRM; it belongs to the page code).
3. Accreditation in Ukraine and a listing in any directory are not recognition and are never presented as such.

## 10. Time-sensitive claims and `nextReview` (POLICY; defaults TO CONFIRM)

1. **Time-sensitive claims:** fees and other charges; application dates and deadlines; intake dates and intake year; operating status, dated statements and teaching delivery; international admission for an intake; requirements and documents for an intake; preparatory start date and fee; accommodation prices.
2. For these, `nextReview` is **at most** the end of the academic year the source refers to, or the published deadline, **whichever is earlier**.
3. **End of the academic year** (TO CONFIRM). Unless the source gives its own end date, use 30 June of the academic year's closing calendar year (2027-06-30 for 2026/27).
4. **Other claims** (TO CONFIRM): name, website, address, contacts and accreditation get `nextReview` no later than 12 months after `accessed` (for accreditation, the certificate's expiry date if earlier); `founded` may be `null`.
5. When `nextReview` passes, or a newer source appears, the entry becomes `outdated`, the decision becomes `withhold`, and the claim is withheld until it is re-checked. The automatic check belongs to the publication-policy code (another work package).
6. Generic example: a fee for 2026/27 read on 2026-10-12, with no earlier deadline on the page, gets `nextReview` no later than 2027-06-30 under the proposed default; an application window printed as closing on a date D gets `nextReview` no later than D.

## 11. Procedure for one claim (POLICY unless marked)

### 11.1 Before either route

1. Take one row of `research/verification/<slug>/EVIDENCE_REGISTER.md`: its claim path, its lead, the page(s) to open and what to read.
2. Treat the lead as a question to answer, never as a value to confirm.
3. Look at the row's evidence column for earlier entries on the same claim path.

### 11.2 Route A — allow-listed browsing

Owner action first: in the cloud environment settings, Network access, allow the hosts listed in `DIRECTORY_VERIFICATION_PLAN.md` §3 and §10.

1. **Fetch test.** Confirm each host now opens. Set the evidence file's access block to `open`, with the date and a note naming the hosts; add a row to `SOURCE_VERIFICATION_REGISTER.md`.
2. Open the page or PDF named in the row. Note the final URL after any redirect.
3. Check that the page is on the university's own domain (or a government or regulator domain for tier 3) — §6.
4. Find the passage that states the claim. If there is none, record a silent page (§5.1) and stop for this claim.
5. Copy the passage exactly into `quotation`, in its original language. Note the page's own date (`effectiveDate`) and academic year (`academicYear`).
6. Write `statement` and `value` exactly as the record would hold them.
7. Choose `sourceTier` (§6) and check the claim type accepts it (§7).
8. Check the file for other entries on the same claim path. If they disagree, follow §8.
9. Set `status` (§5), `nextReview` (§10), `decision` and, when withholding, `withholdReason`.
10. Save a capture where possible and put its file name in `captureRef`; keep the file outside the repository (TO CONFIRM that Route A captures are expected).
11. Add the entry to `site/data/evidence/<slug>.json`.
12. Only if the status is `verified` and the decision `publish`: update the record claim — `value`, `status: verified`, `source` = `sourceUrl`, `checked` = `accessed`, and a short note. Otherwise the record claim stays `unverified` or `not-published`, with a note naming the page read.
13. Regenerate the register from the repository root: `python3 -I site/scripts/make-evidence-register.py <slug>`. Check the row's evidence cell and section H ("Evidence file check").
14. From `site/`: `npm run test:records`, then the full `npm test`.
15. Record the session in `SOURCE_VERIFICATION_REGISTER.md`.

### 11.3 Route B — owner captures kept outside the repository

1. The owner (or someone the owner names) opens each page listed in section A of the register in an ordinary browser and saves it as a PDF with the browser's print header on (URL and date on every page) or as a full-page screenshot with the address bar visible. File name: `<slug>--NN--short-name.pdf`, where NN is the register's row number. A page that cannot be found, or does not state the fact, is reported as "NOT FOUND" or "SILENT".
2. The captures stay outside the repository and are shared as a folder.

## 15. Tools

Two scripts help a reviewer follow §11 without editing JSON by hand. They add no rule of their own beyond those marked below: they run the rules the code already enforces (the evidence format in `site/src/lib/evidence.mjs`, the publication policy in `site/src/lib/publication.mjs`, and rules R9 and R10 of `site/tests/records-evidence.mjs`) at the moment an entry is recorded. `site/tests/evidence-tools.mjs` tests both on temporary copies of a fixture record; neither has yet been run against a real record, because no official page has been read (§11.4).

| Script | What it does | What it writes |
|---|---|---|
| `site/scripts/capture-intake.py` (Route B) | Lists the captures in a folder outside the repository with size and SHA-256; extracts their text (PDF with `pdftotext` if installed, HTML and `.txt`) into a temporary folder outside the repository; matches file names to the rows of section A of the register; with `--find`, shows each phrase with its file and page number | Nothing in the repository. It refuses a folder inside the repository, a folder that contains it, or a folder inside any git working tree |
| `site/scripts/evidence-entry.mjs` (`npm run evidence:add --` once that entry is in `site/package.json`) | Builds one entry from its options, checks it against the evidence format, resolves its claim path in the record (an unknown path is refused), gives it the next id, and runs the publication policy to say whether the claim would be shown and, if not, why | Nothing without `--write`. `--write` appends the entry. `--apply-to-record` also sets the record claim's `value`, `status: verified`, `source` (= `--url`), `checked` (= `--accessed`) and a short note naming the entry, and only for an entry that is `verified` with the decision `publish` |

**What the entry tool refuses** (nothing is written): an entry that does not match the evidence format (for example a non-https address, a withheld entry without a reason, a date that is not a real date); an unknown claim path; a value the record field cannot hold; an `accessed` date in the future; a `publish` decision without status `verified` or without a quotation; a `publish` decision the policy would not show; `--apply-to-record` for any other entry; `--apply-to-record` that would break rule R9 (international admission `true` for a programme still in `deferredProgrammes[]`, or anything but `true` for one in `programmes[]`: move the programme by hand first); an owner capture without `--capture-ref`, or a capture reference that is a path rather than a file name; any change that would break R10; a repeat of an entry already recorded; a control character in any option or value (only tabs and line feeds are kept in the quotation, statement, method and reasons; a `--quote-file` loses its byte-order mark and has Windows line endings turned into plain line feeds). Two rules are the tool's own: the control-character rule above, and one derived from §11.2 step 1: while the evidence file's access block says `blocked`, a `web-page` or `pdf` entry (Route A, read directly) is refused, and a capture made in an ordinary browser is recorded as `owner-capture` (Route B). The proposed defaults in §10.3 and §10.4 (30 June; 12 months) appear only as warnings, because the owner has not confirmed them (§13 items 1 and 2).

**What the tools never do:** set `publishable`, `lastReview` or open questions; edit the access block; change a tier or any item §13 leaves to the owner; delete or rewrite an entry. The one change they make to an existing entry is `--mark-outdated <id>`, which sets only its `status` (outdated), `decision` (withhold) and `withholdReason`. `--contradicts <id>` records the new entry's side of a conflict only; §8 point 2 asks for both entries to list each other, so the reverse id is added to the older entry by hand, in its own commit (the policy already withholds the claim from either side).

3. **Read the result.** "As the record stands now" normally says *would NOT be shown (not-verified)*, because the record claim is not verified yet.
